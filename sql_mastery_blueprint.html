CREATE TABLE customers (
  customer_id      INT PRIMARY KEY,
  customer_name    VARCHAR(100),
  region_id        INT,
  signup_date      DATE,
  customer_segment VARCHAR(20)   -- 'Enterprise' | 'SMB' | 'Consumer'
);

CREATE TABLE orders (
  order_id    INT PRIMARY KEY,
  customer_id INT,
  employee_id INT,
  order_date  DATE,
  status      VARCHAR(20)        -- 'Completed' | 'Cancelled' | 'Returned'

  order_item_id INT PRIMARY KEY,
  order_id      INT,
  product_id    INT,
  quantity      INT,
  discount_pct  DECIMAL(4,2)
);
LEVEL 01

Foundations — Analyst Day One

The commands you'll write dozens of times a day. Getting the habits right here — filtering before sorting, handling NULLs deliberately — is what makes the later levels easier to optimize.

SELECT · WHERE · ORDER BY · LIMIT
Query Cost: Low
Business ask: The West region sales manager wants the 10 most recent completed orders to spot-check against a customer complaint.
SELECT order_id, customer_id, order_date, status
FROM orders
WHERE status = 'Completed'
ORDER BY order_date DESC
LIMIT 10;
Senior Consultant TipName every column you need instead of SELECT * — even on a "throwaway" query. Cloud warehouses (Snowflake, BigQuery, Redshift) bill by bytes scanned or slot-time, so this habit, formed here, is what stops a 200-column customer table from quietly inflating your compute bill later.
Aggregation: GROUP BY + HAVING
Query Cost: Low–Medium
Business ask: Finance wants total net revenue by product category, but only categories generating over $50,000, for a board slide.
SELECT p.category,
       SUM(oi.quantity * p.unit_price * (1 - oi.discount_pct)) AS net_revenue
FROM order_items oi
JOIN products p ON p.product_id = oi.product_id
GROUP BY p.category
HAVING SUM(oi.quantity * p.unit_price * (1 - oi.discount_pct)) > 50000
ORDER BY net_revenue DESC;
Senior Consultant TipWHERE filters rows before aggregation; HAVING filters groups after. Never put a row-level predicate (like a date range) in HAVING — it forces the engine to aggregate the entire table first, then throw most of the work away.
CASE WHEN — Conditional Bucketing
Query Cost: Low
Business ask: Marketing wants customers bucketed into tenure bands to target a loyalty campaign differently for new vs. long-standing accounts.
SELECT customer_id,
       customer_name,
       CASE
         WHEN signup_date >= DATEADD(month, -6, CURRENT_DATE) THEN 'New'
         WHEN signup_date >= DATEADD(year, -2, CURRENT_DATE)  THEN 'Established'
         ELSE 'Veteran'
       END AS tenure_band
FROM customers;
Senior Consultant TipCASE evaluates top to bottom and stops at the first true condition — order branches from most to least restrictive. Reversing this order is a common bug that silently misclassifies rows without ever throwing an error.
NULL Handling — COALESCE & IS NULL
Query Cost: Low
Business ask: A discount report is showing blank cells because some order_items rows never had a discount applied (NULL, not zero).
SELECT order_item_id,
       COALESCE(discount_pct, 0) AS discount_pct_clean
FROM order_items
WHERE discount_pct IS NULL OR discount_pct = 0;
Senior Consultant TipSQL uses three-valued logic — NULL is never "equal to" anything, including another NULL. WHERE column = NULL always returns zero rows with no error. Use IS NULL / IS NOT NULL for comparisons and COALESCE to supply defaults before arithmetic.
LEVEL 02

Relational Joins

Almost no real report lives in one table. This is where an analyst starts thinking in relationships instead of spreadsheets.

INNER JOIN
Query Cost: Low–Medium
Business ask: Sales ops needs every completed order with the customer's name and region for a regional performance review.
SELECT o.order_id, c.customer_name, r.region_name, o.order_date
FROM orders o
INNER JOIN customers c ON c.customer_id = o.customer_id
INNER JOIN regions r ON r.region_id = c.region_id
WHERE o.status = 'Completed';
Senior Consultant TipCloud optimizers reorder joins for you, so hand-tuning join order rarely helps. What does help: join on raw, well-typed keys. Never wrap a join key in a function (e.g. CAST(a.id AS STRING) = b.id) — it blocks the engine from using partition or clustering metadata to skip data.
LEFT JOIN — Anti-Join Pattern
Query Cost: Low–Medium
Business ask: Customer success wants every customer who has never placed a single order — a dormant/at-risk outreach list.
SELECT c.customer_id, c.customer_name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL;
Senior Consultant TipThis "LEFT JOIN + IS NULL" shape is the standard anti-join for "exists in A but not B." Prefer it (or NOT EXISTS) over NOT IN — NOT IN silently returns zero rows for the entire query if the subquery contains even one NULL.
RIGHT JOIN
Query Cost: Low–Medium
Business ask: HR wants every employee listed, including ones not yet assigned any orders, alongside any orders they have processed.
SELECT e.employee_name, o.order_id
FROM orders o
RIGHT JOIN employees e ON e.employee_id = o.employee_id;
Senior Consultant TipRIGHT JOIN is a mirrored LEFT JOIN — nothing it does is impossible with LEFT JOIN and swapped table order. Most teams standardize on LEFT JOIN only, so every join in the codebase reads in the same direction during review.
FULL OUTER JOIN
Query Cost: High
Business ask: Data engineering is reconciling the CRM customer list against the billing system to find records missing on either side.
SELECT COALESCE(crm.customer_id, bill.customer_id) AS customer_id,
       crm.customer_name AS crm_name,
       bill.customer_name AS billing_name
FROM crm_customers crm
FULL OUTER JOIN billing_customers bill ON bill.customer_id = crm.customer_id
WHERE crm.customer_id IS NULL OR bill.customer_id IS NULL;
Senior Consultant TipFULL OUTER JOIN typically forces a full shuffle of both tables in distributed engines like BigQuery or Redshift. Reserve it for genuine two-system reconciliation jobs — not routine dashboards.
SELF JOIN
Query Cost: Low
Business ask: HR needs each employee listed next to their manager's name for an org directory export.
SELECT e.employee_name AS employee, m.employee_name AS manager
FROM employees e
LEFT JOIN employees m ON m.employee_id = e.manager_id;
Senior Consultant TipA self-join only unrolls one level of hierarchy. For an arbitrary-depth org chart (a report's report's report), reach for a recursive CTE — see Level 3 — instead of chaining more self-joins.
CROSS JOIN
Query Cost: Medium (row count multiplies)
Business ask: Marketing wants a planning matrix of every active paid-search campaign against every region, to allocate a geo-targeting budget before results exist.
SELECT camp.campaign_name, r.region_name
FROM campaigns camp
CROSS JOIN regions r
WHERE camp.channel = 'Paid Search';
Senior Consultant TipRow counts multiply (m × n) on a CROSS JOIN. On a warehouse billed by compute, an accidental cross join — usually a forgotten ON clause — is one of the most common causes of a runaway query bill. Sanity-check the expected row count before you run it.
LEVEL 03

Advanced Analytical SQL

CTEs, subqueries, and window functions — the toolkit that lets you answer "compare this row to its group" questions without exporting to a spreadsheet.

Basic CTE
Query Cost: Medium
Business ask: Build a readable two-step report: compute revenue per customer, then surface only the top spenders for account management review.
WITH customer_revenue AS (
  SELECT o.customer_id,
         SUM(oi.quantity * p.unit_price) AS total_revenue
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.order_id
  JOIN products p ON p.product_id = oi.product_id
  WHERE o.status = 'Completed'
  GROUP BY o.customer_id
)
SELECT c.customer_name, cr.total_revenue
FROM customer_revenue cr
JOIN customers c ON c.customer_id = cr.customer_id
WHERE cr.total_revenue > 10000
ORDER BY cr.total_revenue DESC;
Senior Consultant TipName a CTE for what it represents ("customer_revenue," not "cte1") — it's documentation as much as logic. Don't assume it's materialized for performance: in most engines (Snowflake, BigQuery, pre-12 Postgres) a CTE is inlined and re-planned. Reference it five times in the outer query, and some engines will scan it five times.
Chained CTEs
Query Cost: Medium
Business ask: Build a monthly active-customer cohort view, step by step, for a growth report.
WITH monthly_orders AS (
  SELECT customer_id, DATE_TRUNC('month', order_date) AS order_month, order_id
  FROM orders
  WHERE status = 'Completed'
),
first_purchase AS (
  SELECT customer_id, MIN(order_month) AS cohort_month
  FROM monthly_orders
  GROUP BY customer_id
)
SELECT fp.cohort_month, COUNT(DISTINCT mo.customer_id) AS active_customers
FROM monthly_orders mo
JOIN first_purchase fp ON fp.customer_id = mo.customer_id
GROUP BY fp.cohort_month
ORDER BY fp.cohort_month;
Senior Consultant TipChained CTEs read top-to-bottom like a narrative — that's their real advantage over nested subqueries. Keep each CTE to one transformation; if you can't name it in three words, split it into two.
Recursive CTE
Query Cost: Medium–High
Business ask: HR needs the entire reporting chain — direct and indirect — under the VP of Sales for a reorg proposal.
WITH RECURSIVE org_chain AS (
  SELECT employee_id, employee_name, manager_id, 1 AS depth
  FROM employees
  WHERE employee_name = 'VP of Sales'

  UNION ALL

  SELECT e.employee_id, e.employee_name, e.manager_id, oc.depth + 1
  FROM employees e
  JOIN org_chain oc ON e.manager_id = oc.employee_id
  WHERE oc.depth < 20
)
SELECT * FROM org_chain ORDER BY depth;
Senior Consultant TipAlways cap a recursive CTE with a safety condition (WHERE depth < 20). A single circular manager reference from a data-entry error will otherwise spin an infinite loop against your warehouse's compute credits.
Correlated Subquery — the pattern to recognize
Query Cost: High
Business ask: Flag orders whose value exceeds that customer's own historical average — a classic "compare each row to its own group" question.
SELECT o.order_id, o.customer_id
FROM orders o
WHERE (SELECT SUM(oi.quantity * p.unit_price)
       FROM order_items oi
       JOIN products p ON p.product_id = oi.product_id
       WHERE oi.order_id = o.order_id)
      >
      (SELECT AVG(inner_total)
       FROM (SELECT SUM(oi2.quantity * p2.unit_price) AS inner_total
             FROM orders o2
             JOIN order_items oi2 ON oi2.order_id = o2.order_id
             JOIN products p2 ON p2.product_id = oi2.product_id
             WHERE o2.customer_id = o.customer_id) t);
Senior Consultant TipThis is correct, and it's also the exact anti-pattern flagged in Level 4. The inner subquery re-executes once per outer row. Keep reading — Section 4.3 rewrites this same business question as a single window-function pass.
Window Functions — ROW_NUMBER, RANK, DENSE_RANK
Query Cost: Medium
Business ask: Sales leadership wants the top 3 highest-value orders per region for a quarterly spotlight, with ties handled correctly.
SELECT *
FROM (
  SELECT o.order_id, r.region_name,
         SUM(oi.quantity * p.unit_price) AS order_value,
         RANK()       OVER (PARTITION BY r.region_name ORDER BY SUM(oi.quantity * p.unit_price) DESC) AS value_rank,
         DENSE_RANK() OVER (PARTITION BY r.region_name ORDER BY SUM(oi.quantity * p.unit_price) DESC) AS dense_value_rank,
         ROW_NUMBER() OVER (PARTITION BY r.region_name ORDER BY SUM(oi.quantity * p.unit_price) DESC) AS row_num
  FROM orders o
  JOIN customers c ON c.customer_id = o.customer_id
  JOIN regions r ON r.region_id = c.region_id
  JOIN order_items oi ON oi.order_id = o.order_id
  JOIN products p ON p.product_id = oi.product_id
  GROUP BY o.order_id, r.region_name
) ranked
WHERE row_num <= 3;
Senior Consultant TipRANK() leaves gaps after ties (1, 1, 3); DENSE_RANK() doesn't (1, 1, 2); ROW_NUMBER() never ties. Use ROW_NUMBER() for "exactly N per group" pagination; reach for RANK/DENSE_RANK only when the business genuinely cares about tie semantics, like a leaderboard.
LEAD & LAG — Period-over-Period Change
Query Cost: Medium
Business ask: Finance wants month-over-month revenue change per region to flag declining markets before the quarterly review.
SELECT region_name, order_month, monthly_revenue,
       LAG(monthly_revenue) OVER (PARTITION BY region_name ORDER BY order_month) AS prev_month_revenue,
       monthly_revenue - LAG(monthly_revenue) OVER (PARTITION BY region_name ORDER BY order_month) AS mom_change,
       LEAD(monthly_revenue) OVER (PARTITION BY region_name ORDER BY order_month) AS next_month_revenue
FROM regional_monthly_revenue;
Senior Consultant TipLEAD/LAG replace an older self-join-on-date-offset pattern. They're both more readable and materially cheaper — computed in a single sorted pass instead of a join.
Running Totals & Moving Averages
Query Cost: Medium
Business ask: The ops dashboard needs a cumulative revenue line and a 7-day moving average to smooth out daily noise.
SELECT order_date,
       daily_revenue,
       SUM(daily_revenue) OVER (ORDER BY order_date ROWS UNBOUNDED PRECEDING) AS running_total,
       AVG(daily_revenue) OVER (ORDER BY order_date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS moving_avg_7d
FROM daily_revenue_summary
ORDER BY order_date;
Senior Consultant TipAlways write the frame clause explicitly (ROWS BETWEEN…). The implicit default — RANGE UNBOUNDED PRECEDING — behaves unexpectedly with duplicate ORDER BY values, summing tied rows together. Say ROWS when you mean "this many physical rows."
3.8 — JSON & Semi-Structured Data (UNNEST / FLATTEN)
Query Cost: Medium (row explosion possible)
Business ask: The orders table stores each order's applied promo codes as a JSON array (promotions_json). Marketing wants one row per promotion actually used, to measure uptake per code.
-- BigQuery
SELECT o.order_id, promo AS promotion_code
FROM orders o,
UNNEST(JSON_VALUE_ARRAY(o.promotions_json)) AS promo;

-- Snowflake
SELECT o.order_id, promo.value::STRING AS promotion_code
FROM orders o,
LATERAL FLATTEN(input => PARSE_JSON(o.promotions_json)) AS promo;
Senior Consultant TipUNNEST/FLATTEN turn one row into many — an order with three promo codes becomes three rows. Decide before you aggregate whether a downstream metric (order count, revenue) should be computed at the order grain or the promotion grain; joining flattened output straight back into an order-level total is the most common way analysts accidentally triple-count revenue.
LEVEL 04

Query Optimization for Enterprise Cloud Warehouses

Everything above is correct SQL. This is where a senior data professional's judgment starts to matter — recognizing which correct query is also the one that survives 500M rows and a real compute bill.

4.1 — Reading Execution Plans
Diagnostic step — no data movement
Business ask: A dashboard query that ran in 3 seconds last quarter now takes 45 seconds after a data volume increase. Diagnose it before escalating to the platform team.
EXPLAIN
SELECT o.order_id, c.customer_name
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id
WHERE o.order_date >= '2026-01-01';

-- Snowflake:  EXPLAIN USING TEXT  or the Query Profile UI
-- BigQuery:   the "Execution details" tab on a completed job
-- Redshift:   EXPLAIN, cross-referenced with SVL_QUERY_SUMMARY
Senior Consultant TipDon't look for "does it use an index" — that's an on-prem mental model. In cloud MPP warehouses, check for: (1) full table scans where a partition or cluster filter should have pruned data, (2) a shuffle join on a multi-billion-row table where a broadcast join was expected, and (3) large gaps between estimated and actual row counts, which usually means stale table statistics.
4.2 — Indexing Strategy, Reframed for Columnar Warehouses
Design-time decision
Business ask: An analyst asks, "should I just add an index to make this query faster?" — on a Snowflake, BigQuery, or Redshift table.
-- Traditional OLTP (PostgreSQL / MySQL) — a real B-tree index
CREATE INDEX idx_orders_customer_date ON orders(customer_id, order_date);

-- Snowflake — clustering key, not a B-tree index
ALTER TABLE orders CLUSTER BY (order_date);

-- BigQuery — partitioning + clustering, set at table creation
CREATE TABLE orders
PARTITION BY DATE(order_date)
CLUSTER BY customer_id AS
SELECT * FROM staging.orders;

-- Redshift — distribution key + sort key
CREATE TABLE orders (
  order_id    INT,
  customer_id INT,
  order_date  DATE
)
DISTKEY(customer_id)
SORTKEY(order_date);
EnvironmentMechanismWhat it optimizes
PostgreSQL / MySQL (OLTP)CREATE INDEX (B-tree)Fast point lookups & row-level access
SnowflakeClustering keyMicro-partition pruning on scans
BigQueryPartitioning + clusteringBytes scanned (cost) & pruning
RedshiftDist key + sort keyJoin co-location & block skipping
Senior Consultant TipIn columnar cloud warehouses, "indexing" mostly means designing partition and clustering keys around your most common filter and join columns — most of these engines don't support traditional B-tree indexes at all. Cluster on a high-cardinality column that appears in WHERE/JOIN constantly (like a date), not on a low-cardinality flag like status.
4.3 — Rewriting a Correlated Subquery as a Window Function
Query Cost: Low (was High in 3.4)
Business ask: The exact same question from Section 3.4 — orders that beat the customer's own average — but now it needs to run nightly against 50M+ rows without timing out.
WITH order_totals AS (
  SELECT o.order_id, o.customer_id,
         SUM(oi.quantity * p.unit_price) AS order_value
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.order_id
  JOIN products p ON p.product_id = oi.product_id
  GROUP BY o.order_id, o.customer_id
),
with_avg AS (
  SELECT *,
         AVG(order_value) OVER (PARTITION BY customer_id) AS customer_avg_value
  FROM order_totals
)
SELECT order_id, customer_id, order_value, customer_avg_value
FROM with_avg
WHERE order_value > customer_avg_value;
Senior Consultant TipThis is the single highest-leverage optimization habit for a senior analyst. A correlated subquery re-executes once per outer row — roughly O(n²) behavior. The window-function version computes the same aggregate in one pass per partition. On a 50M-row orders table, this is routinely the difference between a query that times out and one that finishes in seconds.
4.4 — Predicate Pushdown & Partition Pruning
Common silent cost
Business ask: A "quick" query filtering to a single year is scanning the entire multi-year orders table instead of just 2026's partitions.
-- Anti-pattern: wraps the partitioned column in a function — defeats pruning
SELECT * FROM orders WHERE YEAR(order_date) = 2026;

-- Sargable rewrite: direct range comparison, prunes partitions cleanly
SELECT order_id, customer_id, order_date
FROM orders
WHERE order_date >= '2026-01-01' AND order_date < '2027-01-01';
Senior Consultant TipAny predicate that wraps the filter column in a function — YEAR(), CAST(), UPPER(), string concatenation — is "non-sargable." The optimizer can no longer use partition metadata or clustering to skip data, so it scans everything and filters row-by-row afterward. Rewrite filters as direct comparisons on the raw column wherever possible.
4.5 — Column Pruning (Why SELECT * Is Expensive Here)
Common silent cost
Business ask: A dashboard query pulls from a 200-column customer table, but the report only displays four fields.
-- Costly: reads every column from disk in a columnar store
SELECT * FROM customers WHERE customer_segment = 'Enterprise';

-- Cheap: columnar engines only read the columns you name
SELECT customer_id, customer_name, region_id, signup_date
FROM customers
WHERE customer_segment = 'Enterprise';
Senior Consultant TipSnowflake, BigQuery, and Redshift store data column-oriented, so SELECT * physically reads every column from disk even if the report only displays a handful. It's one of the most common — and easiest to fix — sources of both slow queries and inflated compute bills.
Footnote: some modern optimizers can prune unused columns from a SELECT * written inside an intermediate CTE, once they see what the final outer SELECT actually references. Don't rely on this — it varies by engine and query shape, and it disappears the moment the CTE is materialized or reused elsewhere. Naming columns explicitly is still the safer default.
4.6 — Materialized Views for Repeated Aggregations
Trades storage for speed
Business ask: The executive dashboard re-runs the same expensive customer-revenue aggregation (from Section 3.1) dozens of times a day for nearly identical results.
CREATE MATERIALIZED VIEW mv_customer_revenue AS
SELECT o.customer_id,
       SUM(oi.quantity * p.unit_price) AS total_revenue,
       MAX(o.order_date) AS last_order_date
FROM orders o
JOIN order_items oi ON oi.order_id = o.order_id
JOIN products p ON p.product_id = oi.product_id
WHERE o.status = 'Completed'
GROUP BY o.customer_id;
Senior Consultant TipMaterialized views trade storage and refresh cost for query-time speed — right for stable, frequently-repeated aggregations feeding dashboards, wrong for ad-hoc exploratory analysis. Confirm your warehouse's refresh model (auto-incremental vs. full rebuild) before relying on one for near-real-time numbers.
LEVEL 05

Orchestration & Version Control

A bonus level, past pure SQL syntax: how the queries above actually live in a modern data team. This is the shift from "an analyst who writes a query" to "an engineer who ships a model."

5.1 — From Script to Governed Model (dbt / Dataform)
Version-controlled · testable
Business ask: The customer-value query from Section 4.3 keeps getting copy-pasted into new dashboards with small drifts. It needs to become one reusable, tested source of truth other analysts build on top of — not a file on someone's laptop.
-- models/marts/fct_customer_order_value.sql  (dbt)

WITH order_totals AS (
  SELECT o.order_id, o.customer_id,
         SUM(oi.quantity * p.unit_price) AS order_value
  FROM {{ ref('orders') }} o
  JOIN {{ ref('order_items') }} oi ON oi.order_id = o.order_id
  JOIN {{ ref('products') }} p ON p.product_id = oi.product_id
  GROUP BY o.order_id, o.customer_id
)

SELECT *,
       AVG(order_value) OVER (PARTITION BY customer_id) AS customer_avg_value
FROM order_totals
Senior Consultant Tip{{ ref('orders') }} isn't cosmetic — it's what lets dbt (or Dataform's own ref()) build a dependency graph and run every model in the right order, and what lets the same code target a dev schema in testing and a prod schema in production without a single line changing. A hardcoded FROM prod.orders is the fastest way to make a model untestable and unsafe to refactor.
