LEVEL 01

Beginner — Connecting Data & Foundational Visuals

Before any DAX or LOD expression matters, the fundamentals: getting the right data in, in the right mode, and picking a chart that actually answers the question asked.

1.1 — Connecting to Data: Import/Extract vs. Live/DirectQuery
Power BI + Tableau
Business ask: Ops needs the on-time-performance dashboard refreshed nightly from the flight operations database — not a manually exported spreadsheet that goes stale by Tuesday.
  • Power BI — Import mode: data is copied into the model, compressed, and cached. Fast, but only as fresh as the last refresh.
  • Power BI — DirectQuery: every visual interaction sends a live query to the source. Always current, but only as fast as the source database.
  • Tableau — Extract: Tableau's own compressed snapshot of the data, refreshed on a schedule. Analogous to Power BI Import.
  • Tableau — Live connection: queries the source directly on every interaction. Analogous to DirectQuery.
Senior Consultant TipDefault to Import/Extract unless the dashboard genuinely needs to-the-minute data, like a live departure board. Live/DirectQuery re-runs a query against the source for every click, filter, and hover — a popular dashboard in that mode during peak travel days can meaningfully load the operational database it's reporting on.
1.2 — Choosing the Right Chart Type
Power BI + Tableau
Business ask: Leadership wants to see flight volume by route, the on-time percentage trend over the year, and where the route network actually flies.
  • Comparing categories (delays by airport) → bar chart
  • Trend over time (monthly on-time %) → line chart
  • Geographic network (origin–destination pairs) → map / flow map
  • Part-to-whole with 2–3 slices (on-time vs. delayed vs. cancelled) → stacked bar or a small donut — never a pie beyond 3–4 categories
Senior Consultant TipResist the reflexive "let's make it a pie chart" request once you're past 3–4 slices. Humans compare bar lengths far more accurately than pie-slice angles — a plain bar chart of delay causes almost always communicates the comparison faster than a colorful wheel.
1.3 — Filters & Slicers
Power BI + Tableau
Business ask: Regional hub managers want to self-service filter the same network dashboard down to just their own airport.
  • Power BI: visual-level, page-level, and report-level filters, plus interactive slicers on the canvas.
  • Tableau: quick filters per worksheet, plus context filters that apply before other calculations run.
Senior Consultant TipScope slicers to only the visuals that should react to them. A KPI card that changes when a user filters an unrelated chart on the same page reads as a bug to a business user, even when it's technically "working as designed" — and it quietly erodes trust in every other number on the dashboard.
1.4 — KPI Cards & Basic Aggregation
Power BI + Tableau
Business ask: The executive summary needs one headline number: this month's on-time performance percentage.
  • A card/KPI visual showing COUNTROWS(Flights WHERE delay <= 15) / COUNTROWS(Flights)-style aggregation.
  • Both tools support a target/comparison value shown alongside the headline number.
Senior Consultant TipNever ship a bare KPI card. "82% on-time" means nothing to a VP without a comparison — last month, the same period last year, or a contractual target. Pair every headline number with a delta or a target line so the viewer doesn't have to ask "is that good?" in the meeting.
LEVEL 02

Intermediate — Calculated Fields, Parameters, DAX & LOD

This is where a dashboard stops being a pass-through of raw columns and starts answering business-specific questions the source system was never built to answer directly.

2.1 — Calculated Measures: Revenue per Available Seat Kilometer
DAX (Power BI)
Business ask: Finance wants RASK — Revenue per Available Seat Kilometer — a standard airline profitability metric, on the route-performance dashboard.
RASK =
DIVIDE(
    SUM ( Bookings[TicketPrice] ),
    SUMX ( Flights, Flights[Distance_km] * RELATED ( Aircraft[SeatCapacity] ) )
)
Senior Consultant TipWrap every ratio measure in DIVIDE() rather than the raw "/" operator. A route with zero completed flights in a filtered period will otherwise throw a divide-by-zero error that blanks out the entire visual — DIVIDE() lets you return BLANK() or 0 gracefully instead.
2.2 — LOD Expressions: Customer Lifetime Spend
Tableau LOD
Business ask: Marketing wants a booking-level table where each row also shows that customer's total lifetime spend, to flag high-value customers whose current booking is unusually small.
{ FIXED [Customer ID] : SUM([Ticket Price]) }
Placed alongside the row-level [Ticket Price] in the same view, this gives every booking row access to a value computed at the customer grain, not the booking grain.
Senior Consultant TipFIXED expressions compute at the grain you specify regardless of what's on the view — that's the point, but also the trap: FIXED ignores most dashboard filters by default. A "lifetime spend" figure built this way won't shrink when someone filters to last quarter, which is sometimes exactly wrong for the question being asked. Reach for INCLUDE/EXCLUDE, or add the filter to context, when the business actually wants a filtered aggregate.
2.3 — Parameters: One Dashboard, Swappable Metric
Power BI + Tableau
Business ask: The route map should let an analyst toggle between "Revenue," "Passenger Count," and "On-Time %" without maintaining three separate dashboards.
-- Tableau: a calculated field driven by a parameter
CASE [Metric Selector]
  WHEN 'Revenue'     THEN SUM([Ticket Price])
  WHEN 'Passengers'  THEN COUNTD([Booking ID])
  WHEN 'On-Time %'   THEN [On Time Pct]
END
Power BI's equivalent is a field parameter — a small table of field references that a slicer swaps between on the same visual.
Senior Consultant TipParameters make one dashboard do the work of three, but they also make a screenshot ambiguous. Always place a visible label showing the current parameter value directly on the dashboard — otherwise a chart forwarded in an email gets misread as showing a metric it isn't.
2.4 — DAX Time Intelligence: Year-over-Year Delay Trend
DAX (Power BI)
Business ask: Operations wants year-over-year change in average departure delay, by month, to see if a hub congestion problem is getting worse.
Avg Delay PY =
CALCULATE (
    AVERAGE ( Flights[DelayMinutes] ),
    SAMEPERIODLASTYEAR ( 'Date'[Date] )
)

Delay YoY % = DIVIDE ( [Avg Delay Current] - [Avg Delay PY], [Avg Delay PY] )
Senior Consultant TipSAMEPERIODLASTYEAR and every other time-intelligence function require a proper, marked Date table with a contiguous calendar and no missing dates. One gap in the calendar silently breaks the comparison for that period — this is the single most common root cause behind "the YoY numbers look wrong" tickets.
💡 The Magic of CALCULATE — Filter Context

CALCULATE is the only function in DAX that can modify filter context. Every other DAX function evaluates inside the context it is handed — CALCULATE is the one function that can change that context before passing it downstream.

In the measure above, CALCULATE( AVERAGE(...), SAMEPERIODLASTYEAR(...) ) does not simply filter rows — it replaces the current date filter context with last year's equivalent period, then evaluates the average inside that new context. This is called context transition, and it is the mechanism behind every time-intelligence pattern, every "all except this filter" pattern, and most advanced DAX.

Understanding this is the lightbulb moment for intermediate Power BI developers. Once you internalize that CALCULATE = "evaluate this expression inside a modified filter context," patterns like REMOVEFILTERS, KEEPFILTERS, and ALL start to make immediate sense instead of feeling like incantations.

LEVEL 03

Senior — Performance, Grain Alignment & Semantic Modeling

The technical skills that don't show up in a single visual, but decide whether the numbers are trustworthy and whether the dashboard survives 200 concurrent users on a Monday morning.

3.1 — Data Grain Alignment (The Fan-Out Trap)
Impact: High — wrong numbers, not just slow ones
Business ask: A dashboard combining booking-level ticket sales with flight-level delay events is showing revenue figures that are 2–3x too high.
A single flight can have multiple bookings (many rows) and, separately, multiple logged delay events (many rows). Joining these two fact tables directly — booking grain to delay-event grain — duplicates each booking row once per delay event on that flight, inflating every downstream SUM.

The fix: aggregate each fact to a shared grain (e.g., one row per flight) before combining them, or connect both fact tables only through a conformed dimension (Flight, Date) in a proper star schema — never join two fact tables directly.
Senior Consultant TipThis "fan-out" bug is the single most common cause of revenue figures that look implausibly high on a dashboard. Before combining any two tables, ask out loud: "what does one row in each table represent?" If the answer differs, aggregate first or route the relationship through a shared dimension.
3.2 — Semantic Modeling: One Governed Star Schema
Impact: High — governance & trust
Business ask: The BI team is asked to support five new dashboards — delays, revenue, loyalty, route network, crew scheduling — without rebuilding data connections and logic five separate times.
Build conformed fact tables (FactBookings, FactFlightOps) around shared dimensions (DimDate, DimAirport, DimAircraft, DimCustomer) in one governed semantic model — a Power BI dataset or a published Tableau data source — with certified measures that every dashboard author reuses.
Senior Consultant TipOne governed semantic model with certified measures is what actually prevents the "your revenue number doesn't match my revenue number" argument between departments six months later — not a shared style guide or a naming convention. If every dashboard author writes their own RASK measure independently, they will eventually drift.
3.3 — Relationship Cardinality & Cross-Filter Direction
Impact: Medium — silent filter bugs
Business ask: A slicer on Aircraft Model isn't filtering the Bookings table at all, even though the model diagram "looks" fully connected.
In Power BI, relationships have both a cardinality (one-to-many, many-to-many) and a cross-filter direction (single or bidirectional). A one-to-many relationship set to filter only from the "one" side won't propagate a filter placed on the "many" side back upstream.
Senior Consultant TipDefault to single-direction cross-filtering from dimension tables to fact tables, and reserve bidirectional filtering for genuine edge cases like a many-to-many bridge table. Bidirectional filtering can create ambiguous filter paths across a dense model and carries a measurable, avoidable performance cost.
3.4 — Measure Optimization with Variables
Impact: Medium — compounds at scale
Business ask: A route-profitability dashboard used by 200 regional managers takes 15+ seconds to load every morning.
Avg Delay Optimized =
VAR TotalDelay  = SUM ( Flights[DelayMinutes] )
VAR FlightCount = COUNTROWS ( Flights )
RETURN
    DIVIDE ( TotalDelay, FlightCount )
Senior Consultant TipUse VAR to compute an expression once per measure and reference the result, instead of repeating the same aggregation inline multiple times. Without it, the engine can re-evaluate the same filter context repeatedly inside one measure — a cost that's invisible on a sample dataset but compounds badly across millions of rows and dozens of concurrent viewers.
3.5 — Incremental Refresh for Large Fact Tables
Impact: Medium — refresh SLA
Business ask: The Flights fact table holds 10 years of history; a nightly full refresh takes 3 hours and increasingly times out before the morning ops meeting.
  • Power BI: define an incremental refresh policy that partitions the table by date range and refreshes only the most recent partition (e.g., last 7 days) nightly, with a full historical rebuild scheduled rarely.
  • Tableau: configure an extract with incremental refresh on a date field, so only new/changed rows are appended.
Senior Consultant TipPartitioning a large fact table by date and refreshing only the recent partition is usually the single biggest lever for meeting a nightly refresh SLA once history exceeds a year or two — it turns a 3-hour full refresh into a 5-minute incremental one.
3.6 — Row-Level Security (RLS): One Dashboard for Every Regional Manager
Impact: High — governance & scalePower BI + Tableau
Business ask: SkyBridge has 50 regional hub managers, each of whom should see the same route-performance dashboard but filtered only to their own hub — Sydney sees Sydney, Dubai sees Dubai, and neither can see the other's numbers.
The naive solution — clone the dashboard 50 times and set a hard-coded filter on each — is a maintenance disaster. One schema change means 50 edits. One metric update requires 50 republishes.

Senior BI developers solve this with Row-Level Security (RLS): a single dashboard with a dynamic filter that evaluates the identity of whoever is logged in at the moment they open it.
  • Power BI — Static RLS: define roles in Power BI Desktop with a DAX filter expression per role (e.g., [HubCode] = "SYD"), then assign users or AD groups to each role in the Service.
  • Power BI — Dynamic RLS: a single "Security" role whose DAX filter uses USERPRINCIPALNAME() to look up the current user's email against a mapping table that links employees to their permitted hub codes. One role, unlimited managers.
  • Tableau — Row-Level Security: achieved via user filters, data source filters keyed to USERNAME(), or a dedicated entitlements table joined to the data.
-- Dynamic RLS filter expression applied to the Routes table
[HubCode] IN
    SELECTCOLUMNS (
        FILTER (
            ManagerPermissions,
            ManagerPermissions[Email] = USERPRINCIPALNAME ()
        ),
        "Hub", ManagerPermissions[HubCode]
    )
Senior Consultant TipDynamic RLS scales to any number of users without touching the report — adding a new regional manager is a row in the permissions table, not a change in Power BI Desktop. The pattern that separates a senior BI developer from a junior one is this: juniors build 50 dashboards, seniors build one dashboard that knows who is looking at it.
LEVEL 04

UX & Visual Design Principles

A technically correct, well-modeled dashboard can still fail if nobody can read it in the three seconds they're willing to give it. This level is about communication, not computation.

4.1 — The Data-Ink Ratio (Tufte)
Design principle
Business ask: A delay-tracking dashboard is covered in heavy gridlines, 3D bar effects, and drop shadows — stakeholders describe it as "hard to read" without being able to say exactly why.
Edward Tufte's data-ink ratio is the proportion of ink (or pixels) on a chart that directly encodes data, versus ink spent on decoration — borders, gridlines, backgrounds, redundant labels, 3D effects. The goal is to maximize that ratio without losing clarity.
Senior Consultant TipBefore shipping a dashboard, do a deliberate pass removing every gridline, border, and background fill that doesn't encode information. If a chart looks identical — or clearer — after removing an element, that element was pure decoration and was competing with the data for the viewer's attention.
4.2 — Pre-attentive Attributes & Deliberate Color Use
Design principle
Business ask: On a route map showing 40 routes, executives can't quickly spot which ones are underperforming.
Pre-attentive attributes — color, size, position — are processed by the eye before conscious thought. Use one saturated highlight color (e.g., red) for the routes below profitability threshold, and a single neutral gray for everything else, rather than a full categorical rainbow palette.
Underperforming route — the one thing to notice first
All other routes — neutral, recedes
Senior Consultant TipReserve saturated color for the one thing you want a viewer to notice first. A map where every route gets its own bright color makes nothing stand out — it's the visual equivalent of shouting every word in a sentence.
4.3 — Layout & Visual Hierarchy
Design principle
Business ask: Users say they "can't find" the KPI they care about most on a dense operations dashboard, even though it's technically on the page.
For left-to-right readers, eyes tend to land top-left first (an F- or Z-pattern reading flow). Place the single most important KPI there, group related visuals with consistent alignment, and use whitespace deliberately to separate sections instead of relying on borders.
Senior Consultant TipDesign every dashboard to answer the one question its primary user has in the first three seconds, then let them drill down for the rest. If the most-viewed KPI is buried bottom-right, that's a layout defect — not something a user-training session will fix.
4.4 — The Dual-Axis Trap
Design principle
Business ask: A chart plots delay minutes and passenger count on a dual-axis line chart, and leadership keeps reading meaning into the point where the two lines cross.
Dual axes with independent scales can be positioned to make two unrelated metrics appear correlated, simply by adjusting each axis's range. The visual "crossing point" of two independently-scaled lines carries no real statistical meaning.
Senior Consultant TipA dual-axis chart is defensible for at most two closely related, similarly-scaled metrics. The moment someone in the room reads meaning into where two independently-scaled lines cross, the chart has become misleading. When in doubt, split the two metrics into stacked small-multiple charts sharing one x-axis instead.
4.5 — Report Tooltips & Drill-throughs: Clean Surface, Deep Dive on Demand
Design principlePower BI + Tableau
Business ask: The route-performance dashboard is clean and executive-ready, but the operations team also wants to hover over any bar and immediately see that route's delay breakdown by cause, aircraft model, and hour of day — without navigating away or opening a second report.
The tension in dashboard design is between clarity (a clean, uncluttered surface) and depth (all the contextual data an analyst needs). Report tooltips and drill-throughs resolve that tension without compromise.

Report Tooltips (hover): a hidden report page is designated as a tooltip. When a user hovers over any data point — a bar, a map marker, a scatter point — a fully rendered mini-chart canvas appears instead of the default text tooltip. A bar for the SYD–MEL route can reveal a sparkline of that route's 12-month delay trend, a breakdown donut by delay cause, and a count of affected passengers, all without any navigation.

Drill-through (right-click → navigate): a dedicated detail page is configured to accept a filter context from any other page. Right-clicking a bar and selecting "Drill through → Route Detail" passes the selected route into a full-page deep-dive — flight-by-flight log, crew assignments, weather flags — with a back-button to return to the summary.

Together these two patterns implement the Overview → Detail design principle that Tufte calls "zoom and filter": the dashboard's job is to surface the anomaly; the tooltip or drill-through page is the answer to "why?"
Senior Consultant TipA custom report tooltip is the purest expression of the data-ink ratio in interaction design: the summary dashboard stays clean because the detail lives on hover, not on the canvas. If you find yourself adding a second or third chart to a dashboard page to "give context" to the first, stop — you probably need a tooltip page, not more visuals competing for the same space.
